Загальний стан добрий: збірка, typecheck, lint, 188 Android-юніт-тестів і lint проходять; маніфест, банківський listener, callables `backups`/`account`, валідація транзакцій у rules — без проблем. Офлайн→kill→холодний старт і видалення на іншому пристрої (resurrection) обробляються коректно.

**3 найбільші ризики:**
1. **[P2-01] 🔴** `profile_invites` дозволяє `list` — будь-який залогінений користувач бачить усі коди-запрошення і може стати editor у чужому спільному профілі (доведено на емуляторі).

3. **[P2-03] 🟡** Видалення акаунта Rytm стирає `users/{uid}` цілком, включно з даними DoRytm, і видаляє спільний Auth-користувач.

**Не вдалося перевірити:** `tests/firestore-rules.mjs` (потрібне доп. встановлення), Playwright-сьют на Windows (див. Baseline), Compose compiler metrics (потрібна зміна tracked build-конфігу), застарілість версій у `libs.versions.toml`, FX при відсутньому курсі, DST/межі місяця в `MonthSummaryWorker`/sweep, поведінка на реальному пристрої (усе — статично + емулятор rules).

## 3. Реєстр знахідок (✅ підтверджено)

### [P2-01] 🔴 Будь-хто залогінений отримує всі коди-запрошення і вступає до чужого спільного профілю
- Severity: 🔴 Critical · Effort: S
- Де: `firestore.rules:231`
- Доказ:
  ```
  match /profile_invites/{code} {
    allow read: if request.auth != null;
  ```
  `read` = `get` + `list`. Емулятор: `ALLOWED attacker lists profile_invites` → `codes: ['OLDUSED1','SECRET12']` → `ALLOWED attacker redeems` → `ALLOWED attacker reads finance`.
- Сценарій: зареєструватися → `getDocs(collection(db,'profile_invites'))` → взяти невикористаний код (TTL 24 год) → redeem → join → роль editor у чужому профілі. Очікувано: код читається лише за точним id.
- Вплив: читання й зміна фінансів, змін, боргів реальних користувачів, щойно хтось створив запрошення.
- Рішення: `allow get: if request.auth != null; allow list: if false;`. Обидва клієнти читають лише за id (`js/firebase-sync.js` `getDoc`, Android `inviteDocRef(code).get()`). Тест у `tests/firestore-rules.mjs`: `assertFails(getDocs(collection(asB,'profile_invites')))` + `assertSucceeds(getDoc(...code))`.

### [P2-02] 🟡 Viewer повертає собі editor; join/leave можуть переписати `roles` інших
- Severity: 🟡 · Effort: S
- Де: `firestore.rules:132-141` (join), `:145-149` (leave)
- Доказ:
  ```
  && request.resource.data.members == resource.data.members.concat([request.auth.uid])
  && request.resource.data.updatedAt is number
  && ... get(profile_invites/...).data.usedBy == request.auth.uid)
  ```
  Немає обмеження `affectedKeys()` і перевірки `expiresAt`. Емулятор: `ALLOWED viewer leaves (also strips roles)` → `ALLOWED viewer rejoins via old expired invite` → `ALLOWED ex-viewer now writes finance`; `ALLOWED attacker joins + downgrades owner-chosen roles`.
- Сценарій: власник понизив учасника до viewer → leave (видаливши свій ключ із `roles`) → join старим кодом (`usedBy==self` назавжди) → знову editor.
- Вплив: ролі не є межею безпеки, всупереч CLAUDE.md.
- Рішення: join/leave — `diff(resource.data).affectedKeys().hasOnly(['members','updatedAt'(,'lastJoinInviteCode')])`; у join `expiresAt > request.time`. Тести: «leave+rejoin тим самим кодом → fail», «join зі зміною roles → fail».

### [P1-03] 🟡 Віддалені зміни транзакцій губляться, якщо приходять у snapshot разом із pending-записом
- Severity: 🟡 · Effort: S
- Де: `android-app/app/src/main/java/ua/rytm/app/data/ProfileSyncCoordinator.kt:406-415`
- Доказ:
  ```kotlin
  addSnapshotListener(MetadataChanges.INCLUDE) { snapshot, error ->
      if (snapshot?.metadata?.hasPendingWrites() == true) return@addSnapshotListener
      ...
      val changes = snapshot.getDocumentChanges(MetadataChanges.EXCLUDE)
  ```
- Сценарій: Android офлайн додає транзакцію; PWA/учасник тим часом змінює іншу → при поверненні в мережу перший snapshot містить чужу зміну + pending → пропущено; наступний (ack) рахує `documentChanges` відносно попереднього доставленого → чужої зміни нема → Room розходиться з хмарою до холодного старту/refresh.

- Рішення: не пропускати snapshot цілком — застосовувати зміни з `!change.document.metadata.hasPendingWrites()`, або при пропуску позначати TRANSACTIONS dirty для повного resync. Тест на Firestore emulator.
