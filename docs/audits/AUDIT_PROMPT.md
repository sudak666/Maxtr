# Промпт для повного аудиту Rytm

Скопіюй усе нижче лінії в нову сесію Claude Code в цьому репозиторії.

---

Зроби повний аудит Rytm: Android-застосунок (`./android-app`, основний), PWA (компаньйон для ноутбука), Cloud Functions, Firestore rules. Результат: `docs/audits/AUDIT_2026-11-full.md`. Код поки не змінюй, тільки знахідки й план.

## Правила

1. **Спершу прочитай** `CLAUDE.md`, `ANDROID_MIGRATION.md` (чекпоінт угорі), `docs/audits/AUDIT_2026-11.md` і `AUDIT_2026-11-first-run.md`. Не повторюй уже виправлене. Для кожної старої відкритої знахідки скажи: досі відкрита / виправлена / більше не актуальна.
2. **«Сучасність» перевіряй за актуальною документацією, а не з пам'яті.** Знання моделі мають дату відсічки, тож свіжі версії й рекомендації треба шукати (WebSearch/WebFetch: developer.android.com, кількість релізів AndroidX, Kotlin, Firebase release notes, web.dev, MDN, Baseline). До кожного твердження «застаріло» додай посилання на джерело і дату.
3. **«Застаріло» ≠ «погано».** Позначай знахідку лише тоді, коли сучасний варіант дає користувачу або підтримці реальну користь (безпека, швидкість, стабільність, доступність, менше коду). Мода сама по собі не аргумент. Не пропонуй переписувати PWA на фреймворк: це свідоме рішення власника.
4. **Кожна знахідка має докази:** файл:рядок, як відтворити, хто постраждає. Вагомість: P0 (втрата/витік даних, падіння), P1 (помітно ламає UX або безпеку), P2 (борг, що заважає), P3 (дрібниці). Позначай, що перевірено запуском, а що лише прочитано.
5. **Перевіряй, а не вгадуй:** `./gradlew assembleDebug lint testDebugUnitTest`, `npm run build && npm run typecheck && npm run lint`, ключові `tests/*.mjs`, `tests/firestore-rules.mjs` (якщо є емулятор). Якщо підключений телефон (adb), зроби скріншоти головних екранів у світлій і темній темі.
6. Токени важливі: читай вибірково, великі зони віддавай субагентам паралельно, у чат пиши коротко. Перед тим, що потребує дуже багато ресурсу (наприклад, повний перф-прогін на телефоні), спитай.

## Що перевірити

### A. Android: сучасність коду
- Версії в `gradle/libs.versions.toml` проти поточних стабільних (Compose BOM, Material 3 / M3 Expressive, Kotlin, AGP, Room, Navigation: чи є сенс у Navigation 3, Glance, WorkManager, Credential Manager, biometric).
- Архітектура: ViewModel + `StateFlow`, `collectAsStateWithLifecycle`, однонаправлений потік даних, відсутність логіки в Composable, DI (вручну чи Hilt/Koin: чи є реальна проблема).
- Compose: стабільність параметрів, зайві рекомпозиції, `remember`/`derivedStateOf`, `LazyColumn` keys, strong skipping, Baseline Profiles.
- Android 15/16: edge-to-edge, predictive back, per-app language, нові вимоги до дозволів і foreground services, target SDK, вимоги Google Play на 2026.
- Корутини: структурована конкурентність, жодних `GlobalScope`, скасування, обробка помилок.
- Безпека: зберігання PIN і токенів, `allowBackup`, R8, логування чутливих даних, NotificationListener.

### B. Android: UI/UX (як Senior PM + Lead UI/UX дизайнер)
- Відповідність Material 3 / M3 Expressive 2026: типографіка, кольорові ролі, динамічний колір, форми, motion.
- Головні сценарії: додати операцію (кількість тапів), переглянути баланс, бюджет, зміни, борги. Де користувач губиться?
- Доступність: TalkBack (contentDescription, порядок фокуса), розмір цілей ≥48dp, контраст WCAG AA, великий шрифт (200%), темна тема.
- Порожні стани, помилки, офлайн, завантаження, зворотний зв'язок після дії, undo.
- Узгодженість: однакові відступи, іконки, тексти; українська мова (помилки, кальки з англійської).
- Адаптивність: планшет/розкладний (NavigationRail), альбомна орієнтація.

### C. PWA
- Сучасний веб 2026: View Transitions, Popover API, `<dialog>`, CSS nesting, container queries, `:has()`, Baseline-статус кожного. Що з цього прибрало б наш власний JS (модалки, фокус-трап)?
- Безпека: CSP, XSS через `innerHTML` з даними користувача, service worker кеш.
- Правило з `CLAUDE.md`: PWA ніколи не псує дані Android (невідомі поля зберігаються, жодних скорочених масивів). Перевір кожен шлях запису.
- Core Web Vitals (LCP, INP, CLS), розмір бандла, доступність (клавіатура, екранні читачі).

### D. Бекенд і дані
- Cloud Functions: версії рантайму і `firebase-functions`, ідемпотентність, ліміти, вартість, логування, обробка помилок.
- Firestore rules: обхід через спільні профілі, валідація полів, тести покривають кожну гілку.
- Резервні копії, видалення акаунта, приватність (`privacy.html` відповідає тому, що реально збирається).
- Секрети в репозиторії, залежності з відомими вразливостями (`npm audit`, Gradle dependency check).

### E. Якість і процес
- Тести: що критичне не покрито (особливо синхронізація Android, міграції Room).
- CI: чого бракує (Android CI немає взагалі: чи варто).
- Документація: що в `CLAUDE.md` застаріло або суперечить коду.

## Формат звіту

1. **Підсумок на 10 рядків:** загальний стан, топ-5 проблем, чесна оцінка «наскільки код сучасний» з поясненням (без завищених оцінок).
2. **Розділ «Міф чи правда: ШІ пише застарілий код?»** — конкретно для цього репо: де код справді відстає від 2026, а де він сучасний, з доказами.
3. Таблиця знахідок: ID, вагомість, зона, опис, доказ, рекомендація, оцінка зусиль (S/M/L).
4. План виправлень хвилями (спочатку P0/P1), кожна хвиля = окремий PR.
5. Що не вдалося перевірити і чому.

Після звіту спитай власника, з якої хвилі починати.
